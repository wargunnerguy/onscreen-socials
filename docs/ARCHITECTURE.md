# Architecture

Notes on the parts that are not obvious from reading the code, and the decisions that
would otherwise get undone by someone tidying up.

## The screen is real

Everything inside `.screen` is real DOM at real pixel size — 1206 × 2622, the iPhone 17
panel. Nothing is scaled down and re-upscaled for export.

The zoom slider applies a CSS `transform` to `#stage`. A transform does not affect layout,
so `offsetWidth` / `offsetHeight` stay unscaled and the export comes out at native
resolution whatever the slider says. Two consequences that have already caused bugs:

- The offset that clears the toolbar cannot live on `#stage`, because it would be scaled
  along with everything else and the status bars would slide underneath the bar. It lives
  on `#stagewrap`, which is not transformed.
- `#stage` still occupies its full ~2666px layout box at every zoom, so `applyZoom()` sets
  an explicit height on `#stagewrap`. Without it the page scrolls over several screens of
  nothing.

`--bar-h` is written from the toolbar's measured height because the bar wraps to two rows
on a narrow window; a fixed offset is wrong at some width.

## Export

`js/export.js` clones the phone node, wraps it in `<svg><foreignObject>`, loads that as an
image and draws it to a canvas.

**The SVG document cannot fetch anything.** No stylesheets, no fonts, no remote images.
Everything it needs is inlined:

- CSS is fetched once at boot and injected as a `<style>` element. This is why `css/app.css`
  must stay self-contained, and why no rule in it may point `url()` at the network.
- Inter is base64 inside `css/fonts.css`. A `@font-face` with an ordinary URL silently
  fails inside the `foreignObject` and the export falls back to the system font — which
  is exactly the failure the bundled font exists to prevent.
- Dropped media is already a data URL, because `js/media.js` uses `FileReader`. A `blob:`
  URL would come out blank.

**Runtime custom properties have to be copied onto the wrapper.** `css/app.css` declares
`--dim` and friends on `:root`, and inside a `foreignObject` `:root` matches the `<svg>`
element — so the injected stylesheet reimposes its own defaults over anything the UI has
set on `document.documentElement`. Before this was fixed, every export came out at the
stock 25% dim no matter where the slider was. `LIVE_VARS` in `export.js` is the list;
anything new that the UI changes at runtime has to be added to it.

**Videos cannot cross the boundary.** Each is replaced by a canvas still of its current
frame. Exports of video slots are one frozen frame, by nature.

**The corners are transparent.** Nothing paints a page background into the clone, so the
area outside the phone's rounded frame keeps a real alpha channel. The green backdrop is a
preview convenience. This is worth knowing before someone "fixes" the missing background.

**Icons must be live SVG nodes, not `<use>` references.** The clone is serialised into a
standalone SVG document, where a `<use href="#id">` pointing at a sprite outside that
subtree resolves to nothing. `js/icons.js` expands `<i data-icon>` into real inline SVG at
boot for this reason.

## Why the chrome is not emoji

The original drew its platform chrome with emoji and fullwidth characters — `♡ 💬 ↪ 🔖 ＋
☰ ⌕ ⋯`. Those rasterise from whatever emoji font the OS ships, so the same export made on
Windows and on macOS came out visibly different. For a tool whose only output is a PNG
that has to match across machines, that was the worst detail in the file.

Emoji inside *user-editable* text still come from the OS font. That is unavoidable without
shipping a colour emoji font, which is ~10 MB.

## Fonts

`css/fonts.css` is generated by `scripts/build-fonts.mjs` and should not be hand-edited.

It builds two faces per weight instead of using Google's stock `latin` + `latin-ext`:
`latin-ext` is ~83 KB per weight because it carries IPA, Latin Extended Additional and
phonetic blocks nothing here will type. Requesting an explicit character set with `?text=`
gets the same practical coverage in ~8 KB. The whole file is ~130 KB rather than ~700 KB.

There is no 800 weight. It was used by exactly one rule (`.fb .pname`) and an extra weight
costs ~55 KB; that rule uses 700.

Characters outside the bundled set fall back to the system font. The set covers Baltic,
Polish, Czech/Slovak, Hungarian, Turkish, Romanian and Croatian — widen `EXTRA` in the
build script if you need more.

The cover photo is draggable vertically (`js/cover.js`). Because it is sized to fill the
width there is never horizontal slack, so only the vertical crop is a choice — which is
what Facebook lets you drag too. The offset is stored in real pixels next to the image in
the account's media record, so it reloads, travels in a preset and reaches the export.
Pointer travel is divided by the stage scale, since the stage is CSS-scaled for viewing.

Avatars are linked (`js/avatars.js`). An account's picture appears in five slots and is
almost always the same image, so a dropped picture goes to all of them; Alt confines it to
one, which then opts out until dropped on again without Alt.

The opt-out is a stored flag, not something inferred from comparing the images. The first
attempt compared each slot against the picture they were sharing, which cannot tell
"change the picture everywhere" apart from "give this one slot something different" —
both look like a drop on a slot that is currently in step, and the test caught it spreading
an intended override across all five.

## Presets

Accounts are data, not code. `js/presets.js` merges four sources — an inline demo, the
files listed in `presets/index.json`, `presets/local.json`, and whatever the user loaded
by hand — with later sources winning on a key clash. The inline demo exists so the app
still works when every fetch fails.

Presets are also the *output* format: `buildDoc()` writes accounts back out with the
browser's edits merged in, which is what the Save… panel downloads. Load and save are the
same shape, so a file can make a full round trip.

Preset `media` carries avatars and covers as data URLs, keyed by `data-mid`. `validateMedia()`
accepts nothing but `data:` URLs: these files are meant to be passed between people, and a
preset that pointed at a remote image would turn opening it into a callback to whoever
wrote it. Video is never written out — it is session-only everywhere else, and a few
seconds of 1080p would dwarf the rest of the file.

Load order matters and has bitten already. One rule settles it: **a file on disk always
outranks the browser cache.** The cache exists to supply accounts that no file provides,
which is what a deployed site needs; put it any later and editing a preset file appears to
do nothing. Order is inline demo → cache → listed presets → `local.json`.

The same trap exists one level down — saved per-account edits layer over the preset, so an
edited field keeps winning after the preset file changes underneath it. That is correct
while working, but it means "I changed the JSON and nothing happened" is usually stale
browser state rather than a bug. Reset clears one account; Clear saved edits clears
everything, both storage keys included.

`presets/local.json` is only probed when `location.hostname` is local. The fetch failing is
harmless, but the browser logs a 404 regardless, and a public site should not hand every
visitor a console error. On a deployment the Load… button is the way in, and it caches
what it loads.

Chrome language lives in `js/strings.js`, not the presets. The stats labels, buttons
and tab rows belong to the phone's interface rather than to the account — a viewer in
Tallinn sees "jälgijat", not "followers" — so they are marked `data-ui="key"` in the
markup and filled in per account from the preset's `lang`. Account data (bios, counts,
post text) stays in `fields`; only words the platforms themselves render are translated.

## State

Text persists to `localStorage` under `onscreen-socials-v1`; images go to IndexedDB
through `js/store.js`. They shared localStorage originally, which gives the whole origin
about 5 MB and capped each image at 900 KB — a cover photo or a screenshot of a TikTok
grid is past both, so they were silently dropped and the work appeared to vanish on
reload. Both stores are migrated forward on first load.

Values stay data URLs rather than Blobs even in IndexedDB, because the export renders
through an SVG `<foreignObject>` that cannot fetch a `blob:` URL.

Videos are still session-only: a few seconds of 1080p as a data URL dwarfs everything else
and would make every save crawl.

**Media is keyed by explicit `data-mid` names**, not by DOM order. It used to be `'m' +
index` over `querySelectorAll('[data-img],[data-slot]')`, which meant any markup change
silently reattached saved images to the wrong slots. `LEGACY_MIDS` in `js/state.js` is the
one-time translation table from the old scheme and must not be re-sorted.

**Saved fields are layered over the preset, not swapped for it.** A save written before
some field existed would otherwise leave that element untouched, showing whatever the
previously selected account had left in it.

**Quota failure keeps the text.** Images are what blow the ~5 MB origin quota, and text is
what is worth saving, so an over-quota write is retried with media dropped rather than
giving up on saving altogether.

The old `ttk-social-mockups-v1` key is read once and migrated, then left in place rather
than deleted, so a bad migration is recoverable.

## Design decisions worth not undoing

- **No real platform logos ship with the tool.** Colour and layout carry the recognition;
  generic glyphs everywhere else. This is what keeps the project clear of Meta's and
  ByteDance's trademark enforcement, along with keeping platform names out of the product
  name. There is a slot in each top bar for a logo the user supplies, because colour alone
  does not tell an audience which app they are looking at — but those are browser-local,
  never part of a preset, and never in the repository. See `js/logos.js`.
- **The video slot is decorative.** Crop-to-fill, dimmed, bleeding off the bottom edge.
  The profile block is the subject; the post is texture.
- **Instagram and Facebook use a feed post, not a grid**, so landscape footage sits at its
  native ratio with no crop. **TikTok keeps the real 3-wide 9:16 grid** because that
  thumbnail wall is the most recognisable thing about a TikTok profile.
- **Facebook is a Page, not a personal profile.** Follow, not Like — the New Pages
  Experience retired the Like button on Page headers. Posts still have Like.
- **The prop watermark is not suppressed in clean view.** Unlike the `+` placeholders it
  has to survive into the exported PNG, or it would be pointless.

## Not built, on purpose

- **Additional platforms.** Each platform is hand-written markup with no abstraction over
  it. At three, an abstraction would cost more than it saves; revisit around five.
- **A Playwright batch-export script.** The in-browser `All three` button covers it, and a
  script would add a Node toolchain to a project that otherwise needs none. (`build-fonts`
  is a one-off that regenerates a committed file.)
- **Scraping follower counts.** All three platforms put profile pages behind a login wall.
  Driving a browser with a logged-in session works technically but violates their terms
  and risks the account, for a number that is on screen for three seconds. Read it out of
  the platform's own insights instead.
